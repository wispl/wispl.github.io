## Introduction {#introduction}

This is useful for unit tests on functions interacting with hardware. Except we want to mock the hardware out. [Ceedling](https://github.com/ThrowTheSwitch/Ceedling) is a unit testing and also a build system. Suppose we want to test functions interacting with a test sensor, let's call it `astute_sensor`. We start by calling

```sh
ceedling module:create[astute_sensor]
```

Which will create a files `src/astute_sensor.h`, `src/astute_sensor.c`, `test/test_astute_sensor.c`. This part is mostly optionally, you can create your files normally if you want (I prefer this as you have more control). What is more important is configuring your `project.yml` file

As you can see, it automatically creates some files for us. You can configure include, test, and source directories through a yaml file, which will be great for stm32 projects which have rather evil project conventions.

```yaml
# Make sure these are there
:paths:
  :test:
    - tests/**
  :source:
    - source/**
  # This is needed if you are using an include directory
  # :include:
  #   - include/**
  #   -
```

Ceedling bundles Unity (not the game engine, thankfully) and CMock with it. Unity is used for running unit tests and also gives us really useful asserts like `TEST_ASSERT_FLOAT_WITHIN` which allows us to test floats within a margin of error. CMock is the big one as it really simplifies mocking functions for us. And mocking functions is going to be the key to unit testing without the hardware. Suppose you have header file like the following `hal.h` file

```c
#ifndef HAL_H
#define HAL_H

// Put all your functions and structs here
bool hal_i2c_read(struct i2c_handle handle, void* buffer, uint8_t size);
bool hal_spi_read(struct spi_handle handle, void* buffer, uint8_t size);
//...

#endif  // MOCK_HAL_H
```

Note that if you use something like STM32's HAL library or any other vendor library, you can also mock those directly. If your unit tests are located with your firmware repository, than you can simply just do `#include mock_stm32h7xx_hal.h` for the most part, but there might be issues due to the file also including other files. It might be simpler to just use a stub file or use a thin abstraction over the stm32 hal.

Otherwise, if you have reusable code which doesn't rely on a particular cortex and have it separate from the firmware code, you might have to get more creative: for example using a thin abstraction or a stub file, as stated above. In our case, our thin abstraction is the `hal.h`

```c
#include "astute_sensor.h"
#include "hal.h"

// ...
float astute_sensor_read(struct *astute_sensor s)
{
      uint8_t value = 0;
      hal_spi_read(&s->handle, &value, s->data_size);
      // Do some weird algorithm stuff
      return (value * 0.2) + 0.3;
}
// ...
```

Then we head on to write our tests in `test_astute_sensor.c`. For this we have to tell CMock to mock the functions in addition to telling it what functions we are going to call and what values it should return.

```c
#include "unity.h"
#include "cmock.h"

#include "astute_sensor.h"
#include "mock_hal.h"       // IMPORTANT: this handles the mocking

void test_astute_sensor_read_value(void)
{
        // Mock parameters
        struct astute_sensor sensor = {
                .handle = NULL,  // don't care
                .data_size = 1,  // don't care
        };
        float expected = 5.1f;
        float tolerance = 0.1f;
        uint8_t value = 24;

        // Tell CMock what function we want to mock as well as what to return
        // when we do mock it.
        hal_spi_read_ExpectAndReturn(&s->handle, NULL, s->data_size, HAL_MAX_DELAY);

        // Read true, and ignore any extra arguments we don't specify. You
        // might have to add `:expect_any_args` to :cmock: :plugins: in your
        // project.yml
        hal_spi_read_ExpectAnyArgsAndReturn(true);
        // Sets the value of the parameter `value` of `hal_spi_read` return
        // the following fake value. You might have to add :return_thru_ptr
        // to :cmock: :plugins: in your project.yml
        hal_spi_read_ReturnMemThruPtr_value(&fake, sizeof(fake));

        // Now call the function
        float result = astute_sensor_read(&sensor);

        // And check using asserts. You might have to comment outo
        // `UNITY_EXCLUDE_FLOAT` under :unity: :defines: in your project.yml
        TEST_ASSERT_FLOAT_WITHIN(tolerance, expected, actual);
}

// Add more tests if your heart desires more

```

Check the CMock [documentation](https://github.com/ThrowTheSwitch/CMock/blob/master/docs/CMock_Summary.md#generated-mock-module-summary) for more mocks. There are a lot of them! Run `ceedling test:all` to run all tests. For coverage, you should install \`gcovr\` and enable `gcov` under `:plugins:` in `project.yml`. You can then run `ceedling gcov:all` which will generate a pretty html which you can open in your browser. You can do something like the following

```c
static foloat some_helper(struct *astute_sensor s) // GCOVR_EXCL_FUNCTION
{
        // ...
}
```

To ignore functions which you don't care about (like those entirely dependent on hardware) when testing for coverage.


## CMake {#cmake}

Ceedling also tries to be a build system as well, as you can do `ceedling build` to get a release build. Integrating with CMake seems kind of difficult, so I just end up duplicating some configuration between the two. With CMake FetchContent, I have to add

```yaml
# To avoid clobbering cmake's stuff under build
:project:
  :build_root: build/ceedling
# To get headers from dependencies installed by FetchContent
:paths:
  :include:
    - build/_deps/**

```

Which isn't too much work. I know that Ceedling does support fetching dependencies as well, but STM32 primarily uses CMake or Makefiles, which makes integrating Ceedling a bit awkward.


## Permission Denied Errors {#permission-denied-errors}

You might hit this for some reason, the fix is the line below

```sh
chmod -R +w ./build/ceedling/vendor
```

or wherever your ceedling vendor directory happends to be
