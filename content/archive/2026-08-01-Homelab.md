I brought a nice mini-pc a while, the Thinkcentre M715q, and decided to use it as a homelab. I was already using NixOS on my desktops so I thought it would be pretty neat to use it on the homelab too. Although I was spoiled with the amount of choices I have. 

# Nix Services

I could keep it simple and just use NixOS services and than expose them using a reverse proxy

```nix
{
  services.caddy.enable = true;
  services.jellyfin.enable = true;
}
```

It is probably possible to lock-down the systemd service to reduce exposure, but I kind of like to use containers to create a separation between the host and services. It is not necessarily more secure (it can be though!) but I think dynamic stuff like spinning up services should be separate from the host. Also maybe I starting myself enough to start moving the homelab to high availability, which would mean difficult with this set up.

But there is nothing wrong with this approach, you can even use [quadlet-nix](https://github.com/SEIAROTg/quadlet-nix) to use podman containers so there is a little bit more isolation. And you can also have a slightly easier time backing up the volumes. 

# Kubernetes

You can probably use nix to easily bootstrap Kubernetes nodes. With a custom bootstrap and disko you can easily spin up a new node. And with [kubenix](https://kubenix.org/) you can even manage Kubernetes manifests in nix. Though I think if you are going this route, using ArgoCD or Flux and standard GitOps might be a better fit.

This of course is really complex, and requires you to set up a cluster. In return you get HA if you have multiple nodes. But going the GitOps route means part of your homelab isn't being managed by nix, which may or may not be fine for you. One benefit is of course rapid deployments, since you don't have to do rebuilds and such.

# Incus

I find Kubernetes to be too much of an overhead for my use case. But if you really like Kubernetes or want to learn it, then the overhead is basically zero :)

As an alternative to the more complicated options, I decided to use Incus. It is a fork of LXD and its gist is:

>>> Incus is a next-generation system container, application container, and virtual machine manager.

You can create a cluster with three members and get a fairly simple HA setup. As of writing this, the economy is on fire and everything is about as expensive as several golden pianos so I am sticking to my single member setup. But I look to the future of a three cluster setup with dreamy eyes, or something like that.

Anyways, you can use nix to quickly bootstrap the Incus server using

```nix
{
  # Enable incus, and its UI
  virtualisation.incus = {
    enable = true;
    ui.enable = true;
    package = pkgs.incus;
  };
  virtualisation.incus.preseed = {
    # Open up ports for metrics and its api server 
    config = {
      "core.https_address" = ":8443";
      "core.metrics_address" = ":8444";
    };
    # Enable nat and give all pods ip addresses in 10.0.100.1/24
    networks = [
      {
        config = {
          "ipv4.address" = "10.0.100.1/24";
          "ipv6.address" = "none";
          "ipv4.nat" = "true";
        };
        name = "incusbr0";
        type = "bridge";
      }
    ];
    # The default profile
    profiles = [
      {
        name = "default";
        devices = {
          eth0 = {
            name = "eth0";
            network = "incusbr0";
            type = "nic";
          };
          root = {
            path = "/";
            pool = "default";
            type = "disk";
          };
        };
      }
    ];
    # Storage pools
    storage_pools = [
      {
        config = {
          source = "/var/lib/incus/storage-pools/default";
        };
        driver = "dir";
        name = "default";
      }
    ];
  };
}
```

I am currently using the `dir` storage driver with an `xfs` filesystem but that is probably a mistake. A better idea is probably using `btrfs` or `zfs` to allow Incus use storage and image optimizations available to those more featureful filesystems. The metrics endpoint allows you to use the dreadful but integral Grafana, Prometheus, and Loki stack for observability.

When I first started I manage the server using pure bash scripts 

```sh
setfile() {
    instance="$1"
    file="$2"
    path="$3"
    incus file push -p "$file" "${instance}${path}"
    echo "File '$file' pushed to instance '$instance' at '$path'"
}

setdir() {
    instance="$1"
    file="$2"
    path="$3"
    incus file push -pr "$file" "${instance}${path}"
    echo "File '$file' pushed to instance '$instance' at '$path'"
}
```

And then I have a bash script to just run functions like these to start up all my services. Of course this was imperative madness and not declarative goodness, so eventually I decided to move the deployment to using terraform. But with a slight twist… [terranix](https://terranix.org/).

# Terranix

This is really cool, you can use nix to generate a terraform file. Now why would you want to do that? The same reason you are using NixOS! To use nix. Wait that is not it? Oh well. Anyways in `packages/default.nix` I have this call

```nix
{
  pkgs,
  inputs,
}:
{
  server = inputs.terranix.lib.terranixConfiguration {
    system = pkgs.stdenv.hostPlatform.system;
    modules = [ ./server ];
  };
}
```

There is a bit more behind the scenes, but you will have to look at my dotfiles to realize that. But with this, you can do just do `nix build .#server -o config.tf.json` to create terraform file, which you can now run `tofu apply` on.

Now this wouldn't be complete without some nix goodness would it? I have this function defined
```nix
{
  mkInstance =
    {
      name,
      image,
      expose ? { },
      ip ? null,
      volumes ? { },
      files ? [ ],
      configs ? { },
      execs ? { },
      volumeConfigs ? { },
    }:
    mkMerge [
      # Create the volumes
      {
        resource."incus_storage_volume" = genAttrs (attrNames volumes) (volume: {
          name = volume;
          pool = "default";
          config = volumeConfigs;
        });
      }

      # Add instance to list of instance to be exposed via reverse proxy
      (mkIf (expose != { }) {
        modules.server.expose = expose;
      })

      # Create the instance, mapping the volumes and IP as needed
      {
        resource."incus_instance".${name} = {
          # Pass these right through
          name = name;
          image = image;
          file = files;
          exec = execs;
          config = configs;
          # Map volume name to path, and also set static IP if specified
          device =
            (mapAttrsToList (volume: path: {
              name = volume;
              type = "disk";
              properties = {
                path = path;
                source = volume;
                pool = "default";
              };
            }) volumes)
            ++ (optional (ip != null) {
              name = "eth0";
              type = "nic";
              properties = {
                "network" = "incusbr0";
                "ipv4.address" = ip;
              };
            });
        };
      }
    ];
}
```

Which allows me to easily create instances like so

```nix
(utils.mkInstance {
  name = "syncthing";
  image = "docker:syncthing/syncthing";
  expose = {
    "sync" = "syncthing.incus:8384";
  };
  volumes = {
    "syncthing-data" = "/var/syncthing";
  };
})
```

The function automagically creates the volumes and attaches it to the instance. There are still a few rough spots with the function, like how to handle volume mount permissions (currently using `volumeConfigs`) and how to pre-populate volumes with files. 

But the cool part is this: using some nix-fu I can use the `expose` field to automatically create configurations for my `caddy` and `authelia` instance. Watch this…

```nix
(utils.mkInstance {
  name = "caddy";
  image = "docker:caddy:2.11";
  volumes = {
    "caddy-data" = "/data";
  };
  files = [
    {
      target_path = "/etc/caddy/Caddyfile";
      content =
        # yaml
        ''
          auth.${cfg.name}.internal {
            reverse_proxy authelia:9091
          }

          ${concatLines (
            lib.mapAttrsToList (name: value: ''
              ${name}.${cfg.name}.internal {
                 forward_auth authelia:9091 {
                   uri /api/authz/forward-auth
                   copy_headers Remote-User Remote-Groups Remote-Email Remote-Name
                 }
                 reverse_proxy ${value}
              }
            '') cfg.expose
          )}
        '';
    }
  ];
  ip = proxyIP;
})
```

The concat portion automatically uses the attribute set exposed `exposed` to create entries in caddy to reverse_proxy the services. Authelia is a bit more complicated but the overall method is the same. This is something that would be difficult to do using just kubernetes. And yeah, regular nix variables are available here too.

# Comin

And now the missing portion… [comin](https://github.com/nlewo/comin). With comin, you can have your servers watch your dotfiles repository for changes. Once you make commit, and hopefully run some CI/CD checks to verify it is good (I don't by the way…), comin pulls the changes in and then builds and deploys.

And since we are using Incus, our system doesn't change that much so builds do not take that long. At the very least, the kernel, Incus, and some other system packages will be upgraded. And using comin's `postDeploymentCommand`, you can automatically build and push terranix changes. 

# The End?

Overall, I think this is a pretty simple but efficient setup. I have not gotten around to a three cluster setup or adding a NAS yet, but I am certain using nix will greatly simplify the setup. I can automatically provision the file server, or add the server as a node to the Incus cluster.
